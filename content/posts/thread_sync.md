In the last couple of posts, I've discussed race conditions and what causes them, in pursuit of understanding multithreading.

Today, I want to look at an old solution to this problem: **Peterson's Algorithm**. But first, let's understand why our "obvious" solutions don't actually work.

## What's a Critical Section?

A critical section is any part of code where shared data might be accessed while being concurrently modified by multiple threads.

Let's understand this by looking at code:

```c
#define ITERATIONS 1000000

long counter = 0;

void *increment(void *arg) {
    for (long i = 0; i < ITERATIONS/2; i++) {
        // Critical section
        counter++;
    }
    return NULL;
}
```

Here, `counter++` is the critical section. Multiple threads are trying to increment the same variable at the same time.

Previously, I wrote about what causes these race conditions, so I'll give a quick summary:

> Even `counter++` is not atomic. It takes multiple CPU instructions to complete, and the CPU can interrupt execution at any point and switch to another thread.

For example, the CPU might interrupt `counter++` **before** the increment is stored and switch to another thread. The other thread increments the counter successfully, then returns CPU to the interrupted thread. The first thread already computed the value (just not stored it yet), so it updates the counter with an outdated value. The counter increases once instead of twice.

This happens unpredictably, and the result varies every time you run the program.

## My First Attempt: A "Simple" Flag

The first approach I tried was to use another variable to prevent the second thread from incrementing the counter while the first thread is still incrementing it.

Something like this:

```c
#define ITERATIONS 1000000

long counter = 0;
bool is_safe = true;

void *increment(void *arg) {
    for (long i = 0; i < ITERATIONS/2; i++) {
        while (!is_safe);
        is_safe = false;
        counter++;
        is_safe = true;
    }
    return NULL;
}
```

What I'm trying to do here is prevent the second thread from incrementing the counter while the first thread is still incrementing it. The counter can't be incremented while `is_safe` is `false`, so the second thread can't increment until the first thread resets it to `true`.

**But since `is_safe` is shared by all threads, we're just moving the problem somewhere else.**

### Why This Fails

Let's look at the assembly code generated by the compiler:


For `while (!is_safe);`:

```asm
.L3:
    movzx   eax, BYTE PTR "is_safe"[rip]
    xor     eax, 1
    test    al, al
    jne     .L3
```

For `is_safe = false;`:

```asm
mov     BYTE PTR "is_safe"[rip], 0
```

For `is_safe = true;`:

```asm
mov     BYTE PTR "is_safe"[rip], 1
```

**See the problem?** These are not atomic operations.

Here's what can happen:

1. `Thread_1` gets interrupted in the middle of `while (!is_safe);` after only performing `movzx eax, BYTE PTR "is_safe"[rip]` (loading the value)
2. `Thread_2` doesn't get interrupted, checks `is_safe` (which is `true`), and sets it to `false`
3. `Thread_2` starts incrementing but gets interrupted in the middle of `counter++`
4. `Thread_1` regains control, compares the old value it loaded (which was `true`), and proceeds to increment **even though `Thread_2` is still in the critical section**

Two threads in the critical section at the same time. **Race condition still happens.**

## Peterson's solution

Look at this algorithm:
```C
int turn; // 0 if thread_0 turn, 1 if thread_1 turn
bool flag[2]; // flag[0]==true if thread_0 wants to enter critical section

flag[i] = true;
turn = j;
while (flag[j] && turn == j);
// Critical section here
flag[i] = false;
```

### Diagram
```
Thread 0 wants to enter: Thread 1 wants to enter:
┌─────────────────┐ ┌─────────────────┐
│ flag[0] = true  │ │ flag[1] = true  │   
│ turn = 1        │ │ turn = 0        │
│ while(flag[1]   │ │ while(flag[0]   │
│ && turn==1)     │ │ && turn==0)     │
│ [wait]          │ │ [wait]          │
└─────────────────┘ └─────────────────┘
│                                  │
└───────────┬──────────────────────┘
            │
One thread wins, one waits
            │
┌───────────┴───────────┐
│ Critical Section      │
│ (only one at a time)  │
└───────────┬───────────┘
            │
flag[i] = false;
```
## Still not done

This looks perfect but we are still not done. If we run the program again with Peterson's algorithm, we'll still not get the correct result.


Our enemies? **Optimizations.**

### Two Types of Optimizations

There are two types of optimizations that prevent Peterson's algorithm from working:

1. **Compiler optimizations**
2. **CPU optimizations** (instruction reordering)

#### Compiler Optimizations

When we write code, each statement expands to multiple CPU instructions, and the compiler may rearrange them to optimize performance.

Imagine the compiler changes the order from:

```c
flag[i] = true;
turn = j;
```

to:

```c
turn = j;
flag[i] = true;
```

This breaks Peterson's algorithm because `turn` is set before the flag, so the other thread might see `turn == j` but `flag[j] == false`, and both threads enter the critical section.

#### CPU Optimizations

Disabling compiler optimizations doesn't solve the problem. The CPU itself may reorder instructions to optimize utilization.

Modern CPUs use techniques like:

- **Store buffers**: Writes might be delayed
- **Load forwarding**: Reads might get stale values
- **Memory reordering**: Instructions execute out of order

This means even if the compiler doesn't reorder, the CPU might, and `flag[i] = true` might not be visible to the other thread immediately

# What I learned

- Peterson' solution is elegant but requires on lots of assumptions to work correctly.
